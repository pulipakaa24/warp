# MetalSim changes on this branch (`metalsim`)

This branch is the Warp build that [MetalSim](https://github.com/pulipakaa24/MetalSim) runs on (see the
section "What was built where" in its [README](https://github.com/pulipakaa24/MetalSim/blob/main/README.md)).

Lineage: [NVIDIA/warp](https://github.com/NVIDIA/warp) → [innate-inc/warp](https://github.com/innate-inc/warp)
(Metal backend, David Dobas / innate-inc; base commit `ce15f6bb`, innate-inc `main` on 2026-09-20) → this branch.

Licence: Apache License 2.0, as upstream. `LICENSE.md` and `licenses/` are unchanged from NVIDIA/warp and
innate-inc/warp (same blob). The changes below modify Apache-2.0 code and are offered under the same licence.

| `b39fee16` | Metal interop entry points: device, queue and buffer handles, foreign `MTLEvent`/`MTLSharedEvent` wait and signal, so a renderer or PyTorch MPS can alias Warp arrays without copies and order work without host synchronization. |
| `b1ec949e` | Captured graphs replay through a Metal indirect command buffer (one `executeCommandsInBuffer` instead of re-encoding each dispatch on the CPU); runtime counters (`wp_metal_counters`: host waits, flushes, host ops, dispatches). `WP_METAL_ICB=0` restores per-dispatch re-encoding. |

| `b9557cb9` | Configurable register-Cholesky bound, `warp.config.metal_register_cholesky_max` (default 40, as before). MetalSim sets 48 for every scene, which puts MuJoCo Warp's 43-dof G1 on the single-SIMD-group register path. |
| `9050cb54` | `nextafterf` (and `__builtin_nextafterf`) in the Metal kernel runtime, bit-exact on float32 bit patterns (Newton's VBD solver needs it). |
| `9ebfad43` | Merge of `metalsim-flex` (`9dcb1406`). |
| `f194006a` | Merge of `9050cb54` into the merge above; the tree MetalSim's results were produced with. |
| `27e63fd1`, `a5b65da1`, `0c9a1fb5` | Metal: register triangular solves in `tile_cholesky_solve` (vector RHS, blocks of at most one SIMD group, matrices up to `metal_register_cholesky_max`): lanes own the factor's columns as in the register Cholesky, forward substitution reduces each row with `simd_sum`, back substitution broadcasts with `simd_shuffle`, no barriers inside the sweeps (the cooperative path pays two per row per sweep). Solve 0.52 -> 0.34 ms per 4096 at n = 43; MuJoCo Warp's G1 step +5.2 %. Summation order only (1.3-3.4e-7 relative). `warp.config.metal_register_solve = False` / `WP_METAL_REGISTER_SOLVE=0` restores the cooperative path. |
| `c44a3f16`, `139385a8` | Metal: compact two-column register layout for the register Cholesky and solve at 33-64 rows (bitwise the generic form). Measured 5-8 % slower at n = 43 / 48; off, `warp.config.metal_compact_register_cholesky` / `WP_METAL_COMPACT_REGISTER_CHOLESKY=1`. |
| `2869a2f7` | Metal: rolled (runtime-loop) form of the register Cholesky, bitwise the unrolled form; 3.4x slower at n = 43 (thread-memory arrays); off, `warp.config.metal_rolled_cholesky` / `WP_METAL_ROLLED_CHOLESKY=<min n>`. |
| `e29950ee` | `tile_cholesky_update_inplace(A, X, count, fill_mode)`: rank-1 Cholesky updates in place (the `mju_cholUpdate` recurrence, additions only), a Metal register form (lanes own rows, SIMD broadcasts) and a scalar path; no adjoint. Used by MuJoCo Warp's archived `MJW_ELLIPTIC_CONE_UPDATE` path. |
| `2834cf31` | Metal: 64-lane register Cholesky (`metal_register_cholesky64`, two SIMD groups per matrix, one column per lane, the tile's own column storage as the per-column exchange with one barrier per column) and a `block_dim` 64 path for the register solve (group 0 computes). Bitwise the 32-lane form at n = 16..48; no faster at n = 43 (factor 0.998 vs 0.989 ms per 4096, solve 0.239 vs 0.326), so MuJoCo Warp keeps 32 lanes; `WP_METAL_CHOL64=0` removes the form. |
| `9df9acee`, `61cf6a4a`, this commit | Metal: split-loop form of the register Cholesky step (`metal_register_cholesky_step_split`: scalar column pivots, the second column's update guarded by the compile-time row index; bitwise the generic step). In a native-snippet context it is 7x faster than the generic step (0.60 vs 4.16 ms per 4096 at n = 43, `scripts/diagnostics/metal_cholesky_residency.py` in MetalSim), on the tile path it measures the same (0.971 vs 0.973 ms), so it is off: `warp.config.metal_chol_split` / `WP_METAL_CHOL_SPLIT=1`. The same benchmark showed that residency (1-8 worlds per threadgroup) does not change the cost. |
| `6bceb39d` | Metal graph replay: indirect execution ranges (`wp_metal_capture_range_begin(range_host)` / `_end`, Python `warp._src.context.metal_capture_range_begin(ranges, index)` / `_end`). The launches recorded between begin and end are replayed with `executeCommandsInBuffer:indirectBuffer:`, the ICB execution range read by the GPU from a 16-byte Metal allocation (uint32 location, length, full length, pad; filled in at the range's end, the `MTLBuffer` resolved at begin because capture-time allocations are retained by the graph). A kernel earlier in the same replay may zero the length and the range's launches are skipped: MuJoCo Warp's exact per-world early exit of its Newton loop at `opt.iterations` on Metal (`MJW_METAL_ICB_EARLY_EXIT`), where `capture_while` has no conditional node. Plain ranges keep the batched `withRange:` replay; `WP_METAL_ICB=0` runs every dispatch as before. |
| `abd59275` | `warp.fem` dispatched bilinear assembly (and `bsr_mm`'s coefficient count) compiled their tile reduction into the one-lane-per-block kernel used off CUDA: the guard `if wp.static(tile_size) > 1` folds only `tile_size`, so the comparison stayed a runtime branch and the `tile_sum` of a 256-lane tile was still sized. With Newton's 6x6 strain blocks that is 75,920 bytes (76,944 at launch) of threadgroup memory against Metal's 32 KB, and `SolverImplicitMPM` failed in `example_mpm_beam_twist` / `example_mpm_snow_ball`. The guard is now `wp.static(tile_size > 1)`, as in the linear dispatch kernel; the kernel needs no threadgroup memory. The dispatched forms match the CPU to float32 round-off; scenes that already ran are bitwise unchanged (`mpm_multi_material`). Test: `TestMetal.test_fem_dispatch_bilinear_wide_blocks`. |
| `67f3407a` | Metal LBVH: `wp.Bvh` / `wp.Mesh` on a Metal device build the LBVH (the default constructor, as on CUDA) instead of falling back to SAH. `lbvh_build_host` in `bvh.cpp` executes the CUDA LBVH kernels of `bvh.cu` (`LinearBVHBuilderGPU::build`: total bounds, Morton keys with the 64-bit group key, stable key sort, key deltas, leaves, `build_hierarchy`, `mark_packed_leaf_nodes`) one thread after the other on the host, into Metal memory; their atomics only pick which child carries on upward, so the tree (node indices, child slots, leaf packing, parents, primitive order, bounds) is bitwise the CUDA one. Refit runs `bvh_refit_kernel` the same way; in-place `Bvh.rebuild()` is LBVH, as on CUDA; LBVH meshes take CUDA's `compute_triangle_bounds`; the solid-angle refit starts at the tree's root. Explicit `"sah"` / `"median"` unchanged. `wp_bvh_get_tree` copies a host or Metal tree's arrays out. MetalSim's tie probe (`mesh_query_ties.py`, closest faces at exact ties around box meshes) against CUDA LBVH: face differences 5013 / 7550 / 3793 -> 243 / 531 / 0 with the FMA-contraction build (294 / 1050 / 0 without), under the Metal-SAH vs CUDA-SAH residual of 437 / 802 / 0, which is query rounding at ties. Tests: `TestMetal.test_lbvh_*`, `TestMetalLbvhHost` (against a NumPy transcription of the CUDA kernels). |
| `35f09f76` | Metal honours the `fuse_fp` module option (Warp's documented default: on): the Metal prelude sets `#pragma clang fp contract(fast)` (or `off` with `fuse_fp=False`), as NVRTC's `--fmad=true` does on CUDA. Before, Metal rounded `a*b+c` twice while CUDA fused it, so the same kernel gave different bits on the two devices. Measured: Metal now reproduces CUDA (Warp 1.16.0, L4) bit for bit on a*b+c, a*b+-c*d, three-term sums and squares, (a-b)*(c-d)+e and c-a*b; Newton's implicit MPM on Metal then tracks the L4 within the L4's own float32 noise. This changes rounding in every Metal kernel (results produced before this commit are not bitwise reproducible with it). Test: `TestMetal.test_fuse_fp_contracts_multiply_add`. |
| `b23d6b81` | Metal GPU parallel utilities (`warp/_src/metal_primitives.py`, hand-written MSL compiled through `wp_metal_load_library` and dispatched with `wp_metal_launch_kernel`, no native change): `radix_sort_pairs` (all six key types, 4/8-byte values, `begin_bit`/`end_bit`) is a stable LSD radix sort with 8-bit digits and reduce-then-scan passes (tile histogram, scan of the [digit][tile] table, scatter; no decoupled look-back, so no inter-threadgroup forward-progress assumption), SIMD-ballot ranking (deterministic, no atomics). Each 16-bit host pass of `sort.cpp` is two 8-bit passes, and a GPU-side plan (one OR-reduction of `radix(key) ^ radix(key[0])`) skips passes whose digit is the same for every key and routes the rest between the two halves and a scratch buffer, so both halves end exactly as on the host. `runlength_encode` (head flags, tile scan, scatter; `run_count` written on the GPU) and `int32`/`int64` `array_scan` (reduce, spine, downsweep; scalars, vectors, strides, in place) likewise; float scans stay on the host. Dispatch shapes depend only on the count; no readback, no device drain, recordable into graphs (which now replay through the ICB path when they had only these host calls). Bitwise equal to the host on every tested input (`warp/tests/test_metal_primitives.py`) and on Newton 1.5.2 MPM trajectories; `example_mpm_twoway_coupling` 252 → 81 ms per frame. `warp.config.metal_gpu_utilities` / `WP_METAL_GPU_UTILITIES=0` restores the host path. |
| `8412a5c8` | Metal GPU BSR assembly (`warp/_src/metal_sparse.py`, Warp kernels plus the GPU radix sort and integer scan of `b23d6b81`, no native change): the topology builders of `bsr_set_from_triplets` (`_bsr_set_from_triplets_native`, so also `bsr_from_triplets`, `bsr_assign`, `bsr_axpy`, `warp.fem` integrate / interpolate) and `bsr_set_transpose` (compact and padded) follow the CUDA algorithm of `sparse.cu`: one key per triplet / source block, `row * ncol + col` (transpose: `col * nrow + row`) with discarded entries (out of range, past `count`, outside the mask, zero blocks under the prune mask) mapped to the sentinel `nrow * ncol`, a stable sort of (key, index) (32-bit keys when the sentinel fits, else 64-bit; bits above the sentinel's skipped), segment heads and an inclusive scan, then binary searches in the sorted keys for the row offsets. No readback (the host-side `nnz` upper bound sizes every dispatch), no device drain, recordable into graphs. Offsets, columns, summed-triplet segments, padded row counts, transpose block maps and status are bitwise the host's. Duplicate triplets are summed in increasing triplet order (stable, as on CUDA); the host `std::sort` is not stable (it differs from a stable order above ~30 triplets), so a block with three or more duplicates can round differently from the host; Newton's MPM assembles no duplicate (row, column) triplets, and its trajectories are bitwise unchanged (`example_mpm_twoway_coupling`, `example_mpm_granular`, 0.25 s, every array of traj / solves). Drains per step 7 -> 0 (twoway) and 5 -> 0 (granular) from BSR assembly; step 78.0 -> 70.5 ms and 70.9 -> 65.4 ms. `warp/tests/test_metal_sparse.py`. `warp.config.metal_gpu_utilities` / `WP_METAL_GPU_UTILITIES=0` restores the host path. |
| `93ed7138` | Metal GPU NanoVDB builder (`warp/_src/metal_volume.py`, MSL compiled and launched like `metal_primitives.py`, no native change): `Volume.allocate_by_voxels` / `allocate_by_tiles` (exact, every builder type), `Volume.rebuild`, `get_voxels` and `get_tiles` run Warp 1.16+'s key-based builder (`volume_builder.cpp`) as GPU kernels instead of draining the GPU and running the host builder on unified memory. Upper-node keys (world points mapped with the explicit `fma` / `floor(x + 0.5f)` arithmetic of `nanovdb::Map::applyInverseMapF(p).round()`, compiled with `fp contract(off)`), keys-only 64-bit LSD radix sort (the `metal_primitives` passes with a keys-only scatter), unique; hierarchy keys, sort, unique of the keys shifted by 0 / 9 / 21; then one thread per node and level (parents by binary search, child / value masks by 32-bit atomic OR on the half word holding the bit, bboxes by int32 atomic min / max, per-leaf voxel counts by atomic add and an integer scan), so the grid depends only on the set of occupied voxels; the double-precision world bbox by a software binary64 `fma` on 64-bit integers in the expression order of `Map::applyMap`; map and voxel size from a cached one-point host build with the same transform. Grid buffers byte for byte the host builder's (`warp/tests/geometry/test_volume_metal.py`: random / clustered / duplicate / single / masked / all-masked / far / half-voxel-boundary points, several voxel sizes, translations and a rotated transform, every tile value type, rebuilds with overflow and invalid input, rebuild replayed from a graph, `fem.Nanogrid` plain and rebuildable; the software `fma` against exact rational arithmetic); Newton 1.5.2 `example_mpm_granular` (plain and rebuildable sparse) and `example_mpm_twoway_coupling` trajectories bitwise unchanged.
